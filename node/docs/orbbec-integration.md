# Orbbec SDK 接入与验证记录

2026-11-11 首版接入时，软件内置 `deepseek-v4-pro` 读取导入的 Orbbec SDK 2.9.0 Windows x64 头文件与示例，生成并通过对话局部修订适配器，完成桌面测试和安装。插件为 `orbbec-rgb@1.0.0`，传感器名称为 **Orbbec RGB 相机**；该轮没有连接到真实相机，`hardware_verified:false`。后续另有内置 Agent 生成的 **Orbbec EGO 双目相机**（`orbbec-ego`），实机记录见下文；两个插件的验证范围分别记录。

## 首版 RGB 插件的使用与范围

在「数据采集 → 添加传感器 → 已安装 SDK」选择 Orbbec RGB 相机。添加卡片后填写可选的设备序列号；留空使用第一台设备。连接成功后进入现有统一开始/停止录制流程。

| 项目 | 当前范围 |
| --- | --- |
| 图像 | RGB8，清单 `[480,640,3]`，请求 640×480@30 |
| 模式选择 | 连接时核对真实设备 profile；不支持就报错，不偷偷改变尺寸或帧率 |
| 格式转换 | 源格式需要转换时调用 SDK FormatConverter；是否受实物支持仍需验证 |
| 其他通道 | Depth、IR、IMU 未接入，不冒充 RGB 或压力数据 |
| 保存 | 原始 RGB MDAQBIN1，理论负载约 27.6 MB/s，尚未验收长期吞吐 |
| 无设备 | 返回“未发现 Orbbec 设备”，释放资源，不输出伪造图像 |

## 首版 RGB 插件已完成的验证

- 模拟 ABI 生命周期检查 **9/9**：覆盖并发启动、停止期间在途等待、拒收首帧、profile 选择与异常释放、取帧/释放错误及 uint64 精度。这些是内存夹具，不是实机测试。
- 真实 Electron UI → preload/IPC → utilityProcess → 插件 host 执行 probe，绑定所需 C 导出并读取厂商 DLL 版本 **2.9.0**。probe 不打开设备。
- 安装后已在实际 UI 验证生成来源徽章、Markdown 回复及传感器选择入口。真实 `PluginManager.connect` 调用厂商 DLL 得到无设备错误，**0 帧、未录制、正常退出**。

最终生成任务为 `01cf01c6-01bf-40a6-8fc7-135b8a923d4e`，修订为 `f46f077f58448d5452f8b2f97431cea30e08a3086b09893e55685a77124fa6a2`；修复通过内置 Agent 的 `replace_draft_text` 写入。尚未验收真实成像、帧率、丢帧、设备同步、长期吞吐或本轮 release 安装包。

## 后续 EGO 双目实机排查（2026-11-11）

`orbbec-ego` 请求左右目 MJPG，经 SDK FormatConverter 转换成每目 1600×1200 RGB8，目标 30fps。它与使用单个 COLOR 传感器的首版 `orbbec-rgb` 不同；现场 EGO 对首版 RGB 插件返回 `Device Component 'color sensor' not found!`，不能通过修改显示名称来解决通道差异。

这次 `SDK process exited (134)` 已定位到公共宿主 `native.copy`：旧实现调用 `koffi.view` 创建外部 ArrayBuffer，Electron 45 的 Node 模式在此发生 N-API 致命退出。使用自行分配的 8 字节原生内存即可复现，不依赖相机或适配器。现在使用 `koffi.decode` 先复制到 V8 自有内存，再让 Buffer 引用该副本；SDK 源帧释放后副本仍有效。真实 Electron 的 8 字节、5.76 MB 图像和 32 MiB 上限回归通过，没有关闭 Electron 内存保护。

相关边界见 [Koffi 外部内存视图说明](https://koffi.dev/pointers) 与 [Electron V8 内存隔离说明](https://www.electronjs.org/blog/v8-memory-cage)。DLL 版本自检没有复制图像，不能覆盖这一桌面运行时兼容性问题。

公共停止预算也从 3 秒调整为宿主 10 秒、父管理器 11 秒；现场 SDK 正常停止曾需约 3.25–3.5 秒，旧期限会误杀正常收尾。连接期限仍是 15 秒，长期无帧仍按既有规则报错。stderr 持续排空且只保留 8 KiB，UI 仅显示已知 N-API/外部缓冲区/内存不足类别，不暴露 SDK 原始日志和凭据，也不把所有 134 都解释成同一个原因。

最新短检查见 `node/.runtime/orbbec-host-diagnostic.json`：

- 检查预算 20 秒，约 5.6 秒初始化、约 14.4 秒取流；左右各收到 **308 帧**，每帧 **5,760,000 字节**。
- 源序号左目 **1..426**、右目 **1..425**，存在序号缺口；这不是稳定 30fps 或零丢帧验收。
- 停止约 3.5 秒，总耗时 23.545 秒后进程 **exit 0**，本轮无 134、无停止超时、无转换报错。
- 另轮已复现 MJPEG 损坏/尾部字节、FormatConverter 返回空和 SDK 队列丢弃，记录在 `node/Log/OrbbecSDK.log.txt`。问题仍待定位；USB2 枚举是现场事实，尚不能认定为根因。

本次修改公共运行时，没有直接修改内置 Agent 生成的双目适配器、没有跳过损坏帧或以假帧补齐。没有录制或导出用户数据。双目原始 RGB 的理论吞吐约 345.6 MB/s、1.24 TB/小时，长期保存和性能尚未验收。

## 原始 MJPEG 接入与实机验证（2026-11-12）

软件内置 `deepseek-v4-pro` 通过实际对话和草稿工具生成 **orbbec-ego@1.1.0**，删除采集路径中的 FormatConverter，按 SDK 返回的实际字节数复制原始 MJPG，并保留源序号与微秒时间戳转换后的精确纳秒字符串。该修订不是外部手写替换适配器。生成任务 `90ede447-a36f-4845-8c4f-a3c2a41a58e8`，修订 `84d998ea6de00d40a7b517da9a13110a515d7ecdcd36efbf4ee7f07b04d056ca`；真实 Electron 的 probe、测试后安装、传感器列表入口与生成来源徽章均已验证。

公共插件契约支持 `encoding:mjpeg`：一条记录保存一帧设备原始 JPEG，`shape` 仍表示解码后的图像尺寸。采集不解码、不二次压缩；结构检查只影响预览是否显示，不删除已交付的坏帧。实际工作台异步解码最多一个任务并保留最新候选，释放位图；源序号缺口、重复、倒序、JPEG 结构异常与应用写盘丢弃分别统计。录制清单保存录制区间的独立质量快照；回放按实际记录长度定位。

用户确认相机直连电脑 USB 3.x；此前 SDK 的 USB2 字符串不能当作真实总线协商速率，也不能据此认定硬件链路故障。

| 实测项目 | 结果与范围 |
| --- | --- |
| 连续取流 | 目标 600 秒；SDK 日志显示运行到停止，最后持久化计数位于 587.303 秒，左右各 17,608 帧，约 29.98 fps/目 |
| 源序号缺口 | 上述计数窗口左目 11、右目 6；无重复、倒序。源序号可能是 SDK 计数，不自动等于曝光序号 |
| 原始录制 | 为控制测试磁盘占用，只录制前 128.196 秒；7,678 帧、4,322,304,133 字节、complete，应用丢弃 0 |
| 文件检查 | 独立逐条回读左右各 3,839 帧，记录数、样本数、字节数一致，应用记录序号缺口 0；10%/50%/95% 位置双目回放均可用 |
| 录制区间源质量 | 左 3、右 2 个源序号缺口；JPEG 结构异常 0。结构有效不等于全部像素经过解码验收 |
| 保存吞吐 | 当前场景约 33.72 MB/s、121.38 GB/小时，相比双目 1600×1200 RGB30 的 345.6 MB/s 减少约 90.24%；画面内容会影响压缩后大小 |
| SDK 进程内存 | 抽样 RSS 89.0–222.9 MiB；抽样在途帧最多 2，没有发现应用队列持续堆积 |
| 实际工作台预览 | 另用实际构建的工作台连续检查 180 秒，左 726、右 725 次解码全部成功，所有位图释放、同时解码最多 1 个，无页面错误；预览限频独立于约 30 fps 采集 |
| 停止 | SDK 日志 10:54:43.115 开始停止，10:54:46.383 完成；没有遗留本次 SDK 进程 |

验证脚本在销毁最后一个隐藏窗口后，Electron 提前退出，导致最终 `result.json` 没有落盘。因此统计只引用实际保存的 587.303 秒快照，不推算最终帧数；录制完整性和回放已在独立 Node 进程重新验证。该开发脚本的退出顺序已修正。诊断脚本曾把 JPEG 字面量嵌入执行代码，其渲染进程内存包含代码缓存开销，不能用于评价产品内存；上表产品预览来自单独的实际 UI 验证。

验证摘要：`node/.runtime/orbbec-mjpeg-endurance/summary.json`；实际 UI 证据：`node/.runtime/mjpeg-ui-validation/result.json`。原始测试文件只在隔离目录生成，验证后保留清单、源时间戳侧文件与六个 JPEG 回放样本，释放约 4.3 GB 测试空间。没有导出用户录制。

**尚未达到长期零丢帧验收。** SDK 2.9.0 仍在应用拿到帧之前报告 JPEG 校验失败，已交付帧的旁路复制无法恢复这些帧。官方 v2.10.6 有相关 JPEG 边界与容错修复，但独立枚举测试无法识别这台 EGO，未替换原 DLL。下一步需要仍兼容 EGO 的修复版 SDK，或厂商提供校验前拒收帧与对应源码。证据和官方修复链接见 [EGO SDK 拒收定位记录](orbbec-mjpeg-sdk-issue.md)。本次没有多小时持续写盘验收，不能把短时约 30 fps 等同于长期零丢失。

## 与直接写 C++ 的区别

这里通过宿主内置 Koffi 调用 Orbbec 的 **C 导出接口**。依据为 SDK 的 `include/libobsensor/ObSensor.h` 和 `h/*.h`；`hpp/Pipeline.hpp` 是这些 C 接口的 C++ 包装。因此不需要厂商另提供 Node 绑定，也没有直接解析 C++ 类、模板或对象 ABI。

它仍使用真实厂商 DLL，但异步 FFI、帧内存复制和 IPC 有额外成本；不能用 DLL 版本自检推断其等同原生 C++ 的吞吐。独立插件进程用于故障隔离，不是权限沙箱。通用约定见 [SDK 插件协议](sdk-plugin-contract.md)。

## 本机开发复现

以下是此次工作区保留的开发脚本，不是用户需要执行的安装步骤，也不随发布包分发。在 `C:\code\数采\node` 下运行；应先等待 Agent 完成写入。

```powershell
node --experimental-vm-modules .runtime/orbbec-agent-lifecycle-check.mjs
```

该脚本只读工作区 `sdk-5576ef90-8586-48c2-ab52-a14053151a25` 的草稿，使用模拟 ABI，不加载厂商 DLL；可通过 `SHROOM_AGENT_WORKSPACE_ID` 选择另一已存在的导入工作区。

```powershell
node .runtime/orbbec-connect-check.mjs
```

此脚本读取已安装插件并执行真实连接，若接有相机可能启动取流，最后关闭资源，不启动录制。本次运行在无 Orbbec 设备的环境中；脚本预期无设备错误，不是实机验收脚本。桌面生产 probe 可通过「SDK 接入 Agent → 测试适配器」复现，修改草稿后必须重新测试再安装。
